r000400.14lossNginx rate limiting typically "breaks" under load due to the **burst** and **nodelay** parameters, not a flaw in the algorithm. Without `nodelay`, excess requests are queued. Under high concurrency, this queue fills instantly, causing high latency and cascading timeouts that feel like a total outage. Additionally, if you use the default `zone` size (e.g., `10m`), the shared memory can fill up under massive traffic. When the zone is full, nginx stops tracking new IPs and applies the limit globally to all traffic (or stops limiting, depending on version), causing erratic behavior. **Fix:** Use `burst` with `nodelay` to drop excess traffic instantly, and increase the `zone` size to safely store all client states.Nginx `limit_req` is per-worker, not global. Under load, each worker enforces its own bucket, so effective limits multiply by worker count. Also, `burst` queues requests; once full, excess returns 503, which spikes under load. Fixes: - Use `limit_req_zone ... zone=...:10m` with shared memory (already shared across workers—verify it's not per-worker). - Set `limit_req_status 429` and tune `burst`/`nodelay`. - For true global limits across instances, use a shared store (Redis) or an edge/WAF layer. Check `worker_processes` and whether limits are applied per `server`/`location` correctly.
r000230.09wingRPC deadline propagation automatically carries the timeout from an incoming request to any outgoing requests made while handling it. The deadline is attached to the gRPC metadata (as `grpc-timeout`) and is automatically injected into child calls by the client stub. This ensures that if a parent request times out, all downstream work is cancelled too, preventing wasted resources. The propagated deadline is always the earliest of the parent's remaining time and any deadline you explicitly set on the child call. You can opt out per-call using `CallOptions` with `WithPropagateDeadline(false)` in Go, or equivalent options in other languages.gRPC deadlines propagate automatically: when a client sets a deadline, the server receives it as the `grpc-timeout` header, and any downstream gRPC calls the server makes inherit the *remaining* time, not the original. So if a client sets 5s and 2s elapse before the server calls another service, that call gets ~3s. This prevents orphaned work and cascading hangs. If the deadline expires, calls fail with `DEADLINE_EXCEEDED`. Note: propagation only works across gRPC hops—if you call HTTP or a queue in between, you must forward the deadline manually.
r000680.11winPostgres connection pooling breaks under load typically due to: 1. **Pool exhaustion** – All connections are checked out, and new requests queue until a timeout. This often happens when transactions are slow or leak (not returned to the pool). 2. **Too many idle connections** – If `max_connections` is high but the pool size is small, the pool becomes a bottleneck. 3. **Transaction pinning** – In PgBouncer transaction mode, a connection is pinned for the whole transaction; long transactions reduce effective pool size. 4. **Prepared statement or session state mismatch** – In transaction pooling, `SET` or `PREPARE` can break if not reset. 5. **Network/backend latency** – Slow queries or lock contention cause connections to pile up. Fix by tuning pool size, setting timeouts, and ensuring connections are always released.Pooling usually breaks because of **exhaustion and queueing**, not pooling itself: - **Pool too small**: requests wait for a connection; latency spikes, then timeouts cascade. - **Pool too large**: exceeds Postgres `max_connections`, causing `too many clients` errors and memory pressure. - **Leaked connections**: a code path doesn't release/return the connection, so the pool drains. - **Long transactions**: hold connections idle-in-transaction, blocking others. - **Per-instance pools**: N app replicas × pool size overshoots the DB limit. Fixes: size pools to `max_connections` minus overhead, set acquire/statement timeouts, always release in `finally`, keep transactions short, and use PgBouncer (transaction mode) for many clients.

r000020.15winVector index recall degrades under load primarily due to resource contention and algorithmic trade-offs: 1. **CPU/GPU saturation**: ANN algorithms (HNSW, IVF) use heuristics that prune the search space. Under heavy concurrency, thread pools become saturated, causing timeouts that force the algorithm to return partial results before exploring enough graph nodes or clusters. 2. **Memory bandwidth**: High query throughput exhausts cache and memory bandwidth, slowing distance computations and causing the search to hit its internal deadline earlier. 3. **Lock contention**: Shared mutable structures (e.g., growing HNSW graphs, inverted lists) serialize access, increasing latency and triggering early termination. 4. **Queueing**: If requests queue behind slow queries, client-side timeouts may abort searches mid-traversal. Mitigations: provision for peak QPS, use read-only replicas, tune `ef_search`/`nprobe` under realistic load, and monitor p99 latency.Recall drops under load mainly because the index is being searched *approximately* under constraints that change: - **Fewer candidates explored**: HNSW `efSearch` or IVF `nprobe` may be lowered, or the search times out and returns partial results. - **Concurrent writes**: inserts/deletes mutate graph or cluster structure mid-search, so traversals miss neighbors. - **Deleted vectors**: tombstones or stale entries reduce effective recall until compaction. - **Memory pressure**: cache eviction or disk-backed segments slow traversal, causing early termination. - **Sharding/merging**: results merged from partial shards can miss true neighbors.
